Approach

Evidence first, then code

The plan behind this build was written under four rules, and the same four governed execution. They are worth stating because two of them changed the plan before a line was written, and one of them is the reason the preflight exists at all.

Rule 1

Cross-reference every claim before acting on it

Every defect in the plan was cited to a file and a line. Two suspicions were dropped mid-pass because the source disproved them: the explicit betas=[…] on files.list looked like a redundant header and is in fact required for session-scoped listing, and two model IDs that looked stale turned out to be current and supported.

Rule 2

Verify API surface, never recall it

Every shape in the build was checked against the reference rather than remembered: the pre-built skill form, the roster description requirement, the budget object's minor-units string, the /mnt/session/outputs/ contract. Recall is where a plausible-looking wrong argument comes from.

Rule 3

Turn fuzzy adjectives into numbers

"Fast", "parallel" and "branded" are not acceptance criteria. Each workstream shipped with a check that passes or fails, written before the code — which is why the acceptance table below can report two non-passes instead of quietly rounding them up.

Rule 4

Prefer deterministic gates over judgement

Where a property can be asserted by a script instead of eyeballed, it is. Repeated failures become tools, validators, docs or policies — not more prompt advice. Every check in smoke_test.py is a fault that once cost a full fan-out to discover.

Why eleven merge commits and not eleven squashes

A squash rewrites the branch SHA, so main no longer contains the branch commit as an ancestor. Every downstream PR's merge-base is orphaned and each child re-shows its ancestors' diffs. That had already happened once, on PR #2, and unwinding it took a rebase plus eight manual ref updates.

Merge commits kept every child diff byte-identical through all nine merges — that is the evidence the strategy worked, not an assertion about it. One cost, learned the hard way: deleting a merged base branch closed its dependent PR rather than retargeting it, so the remaining branches were retargeted first and deleted only at the end.

Finding

The fan-out is the fastest thing in the run

Opening and briefing all four specialists took 0.9 seconds, and every one of them had reported inside 46.1 s. The behaviour the demo exists to show is about 6% of the wall clock. Everything slow here is single-threaded coordinator work.

Finding

Measured speedup: 2.8×, not 4×

The four threads spent 129.7 s of agent time between them — 43.0 Pricing, 20.5 Legal, 45.4 Technical Fit, 20.8 Competitive — inside a 46.1 s window. That is 2.8× against running the same four one after another. Not 4×, because the window is set by the slowest specialist and not the average one.

Finding

The quality loop cost more than the work

Critic round 1, the revision, and round 2 come to 343.2 s — 44% of the run, more than everything before the first draft. Building and visually verifying the document is another 179 s. The proposal itself was written in the first four and a half minutes; the remaining eight went on checking it and rendering it.

Evals

Three layers, and not a test suite among them

There is no tests/ directory, no fixtures, no CI, and no test dependency in requirements.txt. What this build has instead is one deterministic preflight that runs before any spend, one adversarial judge that runs inside the session, and seven outcome checks written before the build and graded after it. Each layer catches a different class of failure. One class is still uncovered, and it is named at the bottom of this section.

Layer 1 · deterministic · pre-spend

The preflight

smoke_test.py — four checks, asserted against the live API rather than fixtures. It creates nothing, updates nothing and starts no session, so it costs nothing to run as often as you like. It stops at the first failure, and every failure message names the script that fixes it.

State files exist · every recorded agent resolves and carries a non-empty description · the coordinator's roster matches .specialist_ids.json exactly · every mapped skill is actually attached.

Each one is a postmortem. An agent with an empty description that the coordinator therefore never delegated to. A coordinator missing docx that silently emitted markdown. A skill recorded in .skill_ids.json but never attached. Each cost a full fan-out to discover once.

Layer 2 · adversarial · in-session

The critic

The only eval that runs during the run. Three verdicts: SHIP IT, REVISE with up to five specific fixes, or STOP with a reason not to bid. On this run it returned REVISE, then SHIP IT, and caught an arithmetic error the coordinator would otherwise have shipped.

The limit worth naming: it is the model judging the model, one round, against no ground truth. The deliverable's existence is gated externally — report_deliverable() fails loudly when the expected .docx is absent — but its quality rests on a self-report.

Layer 3 · outcome · post-hoc

The acceptance checks

Seven checks committed in the plan document before any code was written, so the grading could not drift to meet the result. Two of the seven did not come back a clean pass, and both are recorded as what they are rather than rounded up.

They are the layer that catches what the other two cannot: whether the thing the swarm produced is actually the thing that was asked for.

Check 4 — why two predicted gaps were right to be absent

The 99.99% ask against our 99.95% standard tier surfaced exactly as intended: named in the executive summary, priced at $120,000/yr, and — the part that makes it credible — with a recommendation not to buy it.

The plan also expected the 250ms–1s streaming-latency weakness and the missing Power Apps connector. Neither appeared. Both are in the technical-fit skill's weak-list, but the RFP asks for neither: it says "real-time ingest from ~40,000 IoT devices" and never mentions sub-second query latency or Power Apps. Grading against requirements the customer did not state would have invented gaps.

The lesson worth keeping: a weak-list earns its place by being available when relevant, not by being recited every time.

The layer that is missing

Nothing checks that a deployed agent still matches the repo describing it

Retrieving the four specialists today and diffing them against create_specialists.py: three match exactly, and one does not. The live Technical Fit Specialist is still running its pre-WS3 system prompt, which names product-overview.md as its capability map instead of the technical-fit skill that WS3 promoted it into. Its description, model and skill attachment are all correct — so all four preflight checks pass, and the drift is invisible.

Why it happened: upload_skills.py attaches skills with agents.update, which bumps the agent version without touching system; and create_specialists.py deliberately refuses to run once .specialist_ids.json exists. Editing a specialist's prompt in the repo therefore has no effect on the live agent until someone rebuilds with --archive-existing.

Why check 4 passed anyway: the weak-list the prompt stopped naming lives in the skill body, and the skill was attached. The agent found it without being told to — which is a point in the skill's favour and not a reason to leave the prompt stale.

By this repo's own rule, that earns a fifth preflight check comparing the deployed system and description against the repo definitions — not a paragraph in a docstring.

The critic has no denominator, so it gets no rate

It found two substantive defects in the draft and three copy edits, and its arithmetic was right — 280 + (12 × 60) = 1,000 TB is 3.5× of 280, not the 2.6× the draft claimed. What nobody knows is how many defects the draft actually contained.

Defects found is not defect coverage. "The critic caught 100% of the errors" would be unfalsifiable here, so it isn't claimed. Making it a rate would mean seeding the draft with a known number of planted errors the way the RFP was seeded with six planted traps — which is the obvious next eval and has not been built.

n = 1, so none of these are frequencies

Every number above describes one session. "6 / 6 traps" means this desk caught MFN once, not that it catches MFN. Turning any of them into a rate you could quote needs repeat runs against the same RFP, and then variants of it.

The cost of finding out is known: $3.04 and thirteen minutes per run. That is the argument for the spend cap being a real feature rather than paperwork — it makes the repetition affordable. It just hasn't been done yet.

Why it isn't more

A coordinator fan-out re-reads the same RFP, the same past-wins file and the same skill bodies across six threads and dozens of turns. Almost none of that is billed as fresh input: 91 tokens of a 1.44M input surface were new. Caching is the reason a six-agent, thirteen-minute session that ends in a six-page Word document lands at three dollars rather than an order of magnitude more.

Output is the half that cannot be cached, and at 70,591 tokens it is where the money went. If this run needs to get cheaper, shortening what the agents write beats trimming what they read.

The default is not free

config.py pins effort for two roles and notes that a role absent from the map "is created without an effort field and runs at the model default". Retrieving the agents shows what that default resolves to: high on all three Sonnet specialists, and no effort field at all on Haiku.

So four of the six agents run at high effort or above, and only two of those four were a deliberate choice. If a re-run needs to get cheaper, that is the first place to look — before touching the coordinator's xhigh.

How the cap behaves, and why it is set at create time

The amount is minor units as an integer string: "1000" is $10.00, and a decimal form like "10.00" is rejected. USD only. One cap is shared across every thread in the session, not per agent.

It is create-only, and its removal is one-way — which is why it is passed at sessions.create and never adjusted afterwards. Reaching it is a pause, not a failure: stop_reason.type == "budget_reached". A session parked there accepts only user.tool_confirmation, user.tool_result, user.custom_tool_result or user.interrupt — a plain user.message is a 400. Start a new session with a higher cap rather than trying to raise this one.

Found in execution

Two defects the plan did not anticipate

Both were silent. Nothing errored, and in one case the output looked entirely plausible — which is the argument for the preflight existing at all.

Silent · shared workspace

The build was adopting strangers' skills

upload_skills.py resolved skills by display_name, assuming the Skills API enforces uniqueness. It does not — two skills with the same display name both create successfully.

This workspace is shared with many forks of the repo, and four of our five skills were resolving to bundles uploaded by strangers three months earlier. Everything ran; the output looked fine.

Identity is now the skill_id recorded in .skill_ids.json, display names are namespaced for Console readability only, and content is pushed with skills.versions.create.

Guard on the wrong half

Rebuilding the coordinator stranded the critic

create_coordinator.py --archive-existing yields a coordinator with no # Critic block while the critic agent stays alive and recorded — and the critic script's guard then refused to re-wire it.

Creating the critic is the expensive part; wiring it is cheap and already idempotent. The script now reuses a recorded critic and re-applies the wiring on every run.

Deviation · WS6

The event loop exits instead of continuing

The plan said to continue on requires_action. Nothing in run_deal_desk.py answers a tool confirmation, so continuing would stream forever. It reports the pause loudly and exits non-zero instead. session.status_idle never means "finished" on its own — the nested stop_reason does.

Deviation · WS4

Refusal shipped instead of idempotence

The plan offered "idempotent, or at minimum refuse with a --force flag". Refusal is what shipped, plus --archive-existing — because agents have no delete, only a permanent archive, so a genuinely idempotent create is not available.
